## 1. What this project is

A Hebrew-first (with English support) financial education platform teaching
technical and fundamental analysis on real price action, plus an embedded AI
assistant that answers both conceptual questions and live questions about
specific companies.

Target direction: **Duolingo + TradingView + AI tutor**.

**Live:** `chart-lab.netlify.app`

## 3. AI architecture

### Matching pipeline (order matters enormously)

`generateAiReply(userText, langCode, lastTopicId, conversationContext)` —
**async**. The 4th argument is optional and new as of Phase 3 (see
"Conversation context: entity memory" below) — every existing call site
that only passes 3 arguments keeps working exactly as before. Steps run in
order; first match wins. Full commentary lives in
`src/ai/engine/matching-engine.js` — this is the summary:

1. Greeting (exact whole-message match only)
2. Browse-topics UI request
3. Calculators (price+EPS → P/E, etc.)
4. User-supplied metric analysis ("my P/E is 40")
5. Scenario detectors (multi-concept situations)
6. **Static ticker match** (curated list, no network) — records the entity
7. **Dynamic ticker match** (symbol_search, network) — see §4 — records the entity
7b. **Entity comparison** ("who is more profitable, A or B") — needs two
    distinct entities already in `conversationContext`
7c. **Pronoun/entity-implicit reference** ("her P/E", "is that high?") —
    needs one active entity in `conversationContext`
8. Moving-average with explicit period (`ממוצע 150`)
9. Normal KB scoring (+ facet extraction, comparison promotion)
10. Meta follow-ups ("explain simpler", "go deeper")
11. `what about X` continuation
12. General short contextual follow-up (≤7 words → reuse last topic)
13. Off-topic fallback

Steps 6–7 sit *before* generic KB scoring specifically because "מה המחיר של
מניית Zillow" would otherwise lose to the generic "what is a stock" entry
(the word מניה appears in the sentence). Steps 7b/7c sit right after 6–7 for
the same reason: "מה ה-P/E שלה" contains the literal string "מה ה-P/E",
which would otherwise match the generic 'pe' KB entry (explaining P/E in
general) before the pronoun ever gets a chance to resolve to the actual
company. **Do not reorder any of this without rerunning `npm test`.**

### Conversation context: entity memory (Phase 3)

`lastTopicId` is a single KB-entry-id string ('pe', 'bear-market', ...) —
enough for "explain simpler"/"is that high?" about a *concept*, but with no
idea a *company* was ever mentioned. `src/ai/context/conversation-context.js`
adds a genuinely separate axis: `{ activeEntity, previousEntity,
activeMetric }`, created once per chat session in `chat-ui.js`
(`aiConversationContext`) and threaded through every call.

- **`recordActiveEntity`** — called whenever a company resolves (steps 6/7).
  Shifts the old active entity into `previousEntity` only when it's actually
  a *different* company — asking two questions about the same company in a
  row doesn't push it out of memory (regression-tested).
- **`recordActiveMetric`** — remembers which stock facet (pe/technical/
  risks/...) was just discussed for the active entity, so "is that high?"
  (which names no metric at all) knows what "that" refers to — the same
  pattern `tryContextualNumberFollowup` already uses for KB concepts.
- **Pronoun detection is split in two**, because they resolve differently:
  `GENERIC_ENTITY_PRONOUN_KW` ("her P/E") names the metric right in the
  message, so resolving the pronoun to `activeEntity` is all that's needed.
  `METRIC_IMPLICIT_PRONOUN_KW` ("is that high?") names no metric — it
  reads `activeMetric` from context instead.
- **Entity comparison** (`looksLikeEntityComparison` + `answerEntityComparison`
  in `stock-intent.js`) fetches both entities and compares only what's
  *actually available* from both — price, monthly change, P/E if
  fundamentals happen to be present. A near-equal monthly change is
  reported as "similar performance," not an arbitrary tie-broken winner
  (a real bug caught by the comparison's own test data, which used
  identical synthetic prices for both mocked tickers). When profitability
  data specifically isn't available for one or both sides, the answer says
  so plainly rather than picking a "winner" on no real basis.
- **Low-confidence resolution never guesses.** `searchAndRankSymbol` in
  `ticker-map-and-resolution.js` now detects when 2+ genuinely different
  companies (distinct tickers, both plausible Common Stock matches) are
  found with nothing to disambiguate them, and returns
  `{ ambiguous: true, candidates }` instead of silently picking the first
  one. `answerAmbiguousCompany` turns this into a short clarification
  question with **tappable candidate buttons** in the UI (each button's
  query names the exact ticker, which is an unambiguous exact-match query —
  tapping one is guaranteed to resolve, not loop back into the same
  ambiguity).

### Entity-aware follow-up chips

Stock-data answers always had `relatedIds: []` — there was no KB entry to
derive chips from, so no follow-up suggestions ever appeared after a
company answer. `entityFollowupChips()` in `chat-ui.js` generates
suggestions from the answer's own `entityContext` (which facet was just
answered — never suggest asking the same thing again) plus
`conversationContext.previousEntity` for a comparison suggestion — which
only appears when a *real* second company is actually in context, never a
hardcoded example like "compare to AMD" baked into the UI.

### Facets (scope control)

Entries may carry `facets: { def, pros, cons }`. `detectFacet()` reads the
question's intent; if a facet is requested and exists, **only that facet is
returned**. Currently on: fibonacci, etf, take-profit, stop-loss. Extending
facets to more entries is the single highest-value AI improvement available
and is P1 work, not done in this phase.

### Order-independent comparisons

A comparison entry can declare `sides: [idA, idB]`. `findComparisonBySides()`
promotes it whenever BOTH referenced entries' own keywords match, in
**either word order** — derived from keywords those entries already need for
standalone matching, so nothing is duplicated. This replaced a pattern of
hand-listing every word order as a separate keyword phrase (which is exactly
the one-off-patch trap the entity-resolution side fell into with SanDisk/
Fiverr) for the two entries where it applies (`bull-vs-bear-market`,
and any future clean "just A vs B" comparison). Entries whose comparison is
about a specific ASPECT rather than the two things generally (e.g.
`stocks-vs-bonds-safety`) keep explicit keyword phrases — bare co-occurrence
of "stock" and "bond" shouldn't always mean "asking about safety".

Full details: `docs/AI_ENGINE.md`.

## 4. Market data architecture (implemented)

### Provider abstraction

```js
// src/ai/market/provider-interface.js documents the contract:
{
  id, isDemo, sourceLabel, hasApiKey(),
  async getQuote(ticker), async getHistory(ticker, days),
  async getFundamentals(ticker), async searchSymbol(query)
}
```

Two implementations exist today, both fully working:

- **`TwelveDataProvider`** (`twelvedata-provider.js`) — the live provider.
  Key lives in this file, in plain sight — see the file's own header comment
  for why (it's a public static site; the key is visible via view-source
  regardless of where it's placed) and the shared-quota math (800 req/day,
  ~2-3 req per stock question).
- **`DemoProvider`** (`demo-provider.js`) — zero network, zero key.
  Deterministic (seeded per-ticker, same inputs → same outputs), and every
  value it returns carries `isDemo: true` through to the formatted answer
  text (verified in `tests/market/provider.test.js` — the actual answer
  string is checked for the label, not just an internal flag).

`src/ai/market/index.js` is the only file that knows which provider is
active (`getActiveMarketDataProvider()` / `setActiveMarketDataProvider()`).
Everything above it — the AI's intent/formatting layer, the UI's stock
card — depends only on `getMarketData(ticker)`'s return shape.

**Gotcha already hit once:** top-level `const DemoProvider = {...}` does NOT
become a `window` property in a plain script (same underlying JS behavior
that required `tests/helpers/load-engine.js` to promote const→var for
testing). Code *inside* the same script tag sees it fine via ordinary
lexical scope; code reaching in from outside (browser console, an
automated E2E driver, a future settings panel) needs the explicit
`window.DemoProvider = DemoProvider` export already added in
`market/index.js`. If a new provider is added, export it the same way.

### Rejected alternatives (don't re-litigate without new evidence)

| Source | Verdict |
|---|---|
| Yahoo Finance | No CORS; 401s since 2025. |
| Finnhub | Officially "does not support CORS, need backend". |
| IEX Cloud | Discontinued 2023. |
| marketdata.app | Has CORS, but license forbids public websites. |
| Stooq | Began requiring a CAPTCHA-issued key April 2026. |
| TradingView | Has no public data API at all — widgets are display-only. |

### Entity resolution (Hebrew company names → tickers)

Full pipeline documented in `docs/MARKET_DATA.md`. Summary: curated static
list (fast, no network, best Hebrew phonetic coverage) → dynamic fallback
(filler-word stripping → combinatorial Hebrew transliteration → symbol
search → leverage/derivative filtering → ranking). Every stage has a
regression test in `tests/market/entity-resolution.test.js` tied to a real
bug that was actually hit (SanDisk's leveraged ETP, Gauzy's combined
vav+yod ambiguity, Mobileye's first letter being eaten by prefix-stripping).

## 5. Storage & router (new this phase)

### `src/core/storage.js`

Namespaced (`chartlab:v1:`), versioned, private-browsing-safe wrapper.
Currently backs `theme` and `lang` preferences. Migrated the two pre-existing
raw `localStorage` calls (theme only) to it, including a one-time silent
migration from the old unnamespaced key so existing users don't lose their
preference. **This is the foundation for progress/watchlist/quiz/streaks —
not yet built; add one get/set function pair per feature when that feature's
data shape is actually designed, not speculatively now.**

### `src/core/router.js`

Minimal hash-based router (no History API — this is a static site with no
server-side rewrite rules; hash routes never hit the server, so refreshing
any route never 404s). Scope for this phase, deliberately: real
infrastructure, wired to ONE real route (`#ai`, the AI assistant) as proof —
not a migration of the existing 8 lessons into separate routed pages. That's
a separate, larger, higher-risk step (touches working content) and is
intentionally deferred; see §13.

`navigateTo(path)` dispatches **synchronously** (not by waiting for the
`hashchange` event) — an earlier version didn't, and any caller checking the
result immediately after calling it saw stale state. The `hashchange`
listener still exists, for the browser's own back/forward buttons.

The AI overlay is now deep-linkable: loading the site with `#ai` already in
the URL opens the assistant immediately (verified).

## 7. HTML/SEO/accessibility (fixed this phase)

- Meta description, Open Graph tags, canonical URL, `theme-color`, minimal
  web manifest (`static/manifest.webmanifest`, copied by the build — never
  hand-placed in `dist/`)
- **Real browser-locale language detection**, added where there was
  previously none at all (`navigator.language` starting with `he` → Hebrew
  default) plus a persisted explicit choice via storage.js
- `<html lang="en">` in the raw template was deliberately **left as-is**,
  not changed to `he` — the underlying static text content is actually
  written in English by default (Hebrew is swapped in by `setLang()`), so
  changing only the attribute would create a real mismatch (lang says
  Hebrew, text is English) for any crawler or screen reader that doesn't
  execute JS. Making this genuinely correct requires the static baseline
  content itself to be Hebrew — a real content-architecture change, not a
  one-line fix, and out of scope for this phase. Tracked as a known gap,
  not silently declared fixed.

## 10. Things that must NOT break

1. **The 8 lessons and 19 charts.** A global name collision (`sma()`)
   silently broke every chart once — namespace carefully. `chartColors()`
   drifted from the CSS tokens once — keep them in sync when either changes.
2. **`npm test` must pass** before any ship: 403 assertions, 13 files.
3. **Never fabricate a market number.** No fallback guesses, no stale value
   presented as current. Failure must be explicit — verified by a dedicated
   test (`provider.test.js`: "a real fetch failure never produces a
   fabricated number"). Extends to comparisons: never declare a "winner" on
   a dimension (e.g. profitability) neither fetch actually returned data
   for, and never tie-break a near-equal result into a false winner.
4. **Never present delayed or demo data as real-time or real.** Demo Mode's
   label is checked in the actual answer TEXT by a test, not just an
   internal flag — don't let a future formatter change drop it. This now
   also applies through entity-context follow-ups (asking "her P/E?" while
   Demo Mode is active must still be labeled).
5. **Never substitute a leveraged/derivative instrument** for the underlying
   stock — verified by a dedicated test.
5b. **Never silently guess between multiple real, different companies.**
   Low confidence must produce a clarification, not a pick — verified by a
   dedicated test.
6. **RTL correctness** — Hebrew is the primary language.
7. **Pipeline order in `generateAiReply`** — reordering causes silent
   misrouting; `npm test` catches most of this but not all of it (see the
   "מניה תנודתית" case — a passing suite doesn't mean zero remaining
   scoring-tie edge cases). This now includes steps 7b/7c (entity
   comparison/pronoun reference) — they must stay between ticker resolution
   and generic KB scoring, for the same reason ticker resolution does.
8. **Mobile keyboard handling** in the chat overlay (`visualViewport` sync +
   body scroll lock).
9. **Script load order in `scripts/build.js`** — `market/*` before
   `context/*` before `entity/*` before `intent/*` before `engine/*`; core scripts
   (`storage.js`, `router.js`) before both; `routerInit()` and the language
   auto-detect init must run AFTER the AI section, not inline where they're
   conceptually defined, because both depend on functions the AI section
   defines (`renderAiExamples` for language, route handlers for the router).
   This bit twice during this exact phase — see the two "temporal dead
   zone" bugs in the implementation notes.
10. **Never name a new CSS class without checking it doesn't already exist**
    for something unrelated. Happened twice in Phase 4 (`.quiz-opt` collided
    with the 8 lesson-embedded quizzes; `.compare-row` collided with a
    lesson's breakout-comparison layout) — a "descriptive but generic" name
    in a site this size is exactly the kind likely to already be taken.
    `grep` first. Full detail in §14.
11. **`buildSite()`'s two `template.replace(marker, ...)` calls must stay
    function-form**, never a plain string. A string replacement silently
    interprets `$&`/`` $` ``/`$'`/`$$` in the replacement content as special
    patterns — and this codebase's own price-formatting code
    (`` '$'+price.toFixed(2) ``) legitimately contains the literal `$'`
    sequence, which corrupted the entire build once. Full detail in §14.

## 15. Harden & Verify phase (security, integrity, robustness)

Triggered by a read-only Senior Review that found real, confirmed bugs
(not hypothetical) in Phase 4's shipped code. **481 assertions across 17
test files, all passing** (up from 403/13).

**Security — XSS (real, confirmed exploit).** `stock-view-ui.js` and
`compare-ui.js` interpolated user-typed search text and API-derived company
names directly into `innerHTML`. Confirmed exploitable: typing
`<svg onload="..."><b>...</b>` into the Compare search produced a live
`<svg>` with an intact `onload` attribute. **The same root cause existed in
pre-existing code** (`chat-ui.js`'s stock card / stock-detail overlay,
rendering the same API-derived name/exchange/ticker) — found while
verifying it was safe, fixed under the same principle. Fix: new
`escapeHtml()` (`src/core/dom-safety.js`), applied at every dynamic
interpolation point. `quiz-ui.js`, `calculators-ui.js`,
`lesson-progress-ui.js` were audited and confirmed to never have had this
issue (their dynamic values are always static translation strings or
numbers). `tests/ui/xss-safety.test.js` reproduces the exact payload.

**A general router bug, found via this security work.** `navigateTo()`
sets `location.hash`, which schedules an async native `hashchange` event
*in addition to* the synchronous dispatch it already does.
`routerDispatch` didn't guard against re-entering the same path, so the
delayed event fired `onEnter` a second time — harmless for `openAiChat`
(idempotent), but for Stock View/Compare it silently replaced the DOM
mid-search, discarding a just-rendered answer into a detached node. Fixed:
`routerDispatch` is now a no-op when `routerCurrentPath === path`.

**Demo Mode integrity.** `formatRisks` was the one stock-facet formatter
that never called `asOfLine()` — every other facet does — so a
demo-derived volatility number could appear with no provenance label at
all. Fixed, and `provider.test.js` now loops **every** facet rather than
sampling one (exactly the kind of check that would have caught this
originally). Separately, `DemoProvider`'s `searchSymbol` fabricated a
plausible fake company for ANY non-empty text, including ordinary
questions like "מי יותר רווחית?" that reached it as a mis-extracted
candidate. Fixed at the correct point — `resolveTickerDynamic`, *before*
Hebrew transliteration — because after transliteration the same text
becomes unrecognizable romanized text that no longer matches any keyword
list; checking only inside the provider was too late.

**Persistence robustness.** `storageGet` now accepts an optional shape
validator; `getLessonProgress`/`getQuizProgress` use one each.
Corrupted/legacy-shaped stored values (`completed: "not-an-array"`,
`bestScore: 42`) now fall back to defaults instead of throwing
(`progress.completed.push is not a function`) or silently producing
`NaN`/`null` corruption.

**AI pronoun + intent bug.** "מה החסרונות שלה?" (what are its drawbacks?)
after mentioning NVIDIA used to silently answer with a bare price
snapshot — the pronoun resolved the entity correctly but the question
itself was lost. Two-part fix: (1) `risks` facet keywords now include
drawbacks/disadvantages/downsides (he+en); (2) general safety net —
extracted shared `resolveEffectiveStockIntent()`, and
`tryPronounEntityAnswer` now returns `null` (falls through) rather than
forcing a snapshot whenever the resolved intent is the bare default.

**Context expiration.** `activeEntity` used to stay relevant indefinitely.
Simple turn-counter decay in `conversation-context.js`
(`EXPIRE_AFTER_TURNS = 3`, not a wall-clock timeout or semantic drift
detector — a turn count already solves the reported problem). Reset via
`touchEntityContext()` on any genuine touch (direct mention, pronoun
answer, comparison); checked via `expireEntityContextIfStale()` at the top
of `generateAiReply`, before the pronoun/comparison paths can use it.

**Comparison clarification.** "מי יותר רווחית?" with zero or one known
entity now asks which company(ies) — naming the one that IS known when
there is one — instead of falling through to the generic off-topic
fallback.

**UI test infrastructure (Item 7).** `jsdom` installed as a real
`devDependency` (not borrowed from a neighboring directory).
`tests/helpers/dom-harness.js` loads the actual built `dist/index.html`
and provides `waitFor()` — a polling wait, not a fixed `setTimeout` guess;
fixed timeouts were the direct cause of flaky-looking test failures during
this exact phase (traced to the router bug above, not real flakiness).
Committed: `tests/ui/xss-safety.test.js`, `quiz-ui.test.js`,
`calculators-ui.test.js`, `lesson-progress-ui.test.js` — Stock View and
Compare's rendering/search flow are covered by the XSS test file rather
than duplicated in a second file.

## 16. Product features (Phase 4)
Five new routed views, all built on the Phase 2/3 architecture — none of
them introduced a new data source, a new entity-resolution mechanism, or a
new AI capability. That reuse is the point: it's what "prioritize highest-
value features" looked like in practice this phase.

### Build system: two feature-module tiers

`scripts/build.js` gained a second category alongside `CORE_MODULE_ORDER`:

- **`SHARED_FEATURE_MODULE_ORDER`** — pure logic, no DOM
  (`calculators/calculations.js`, `quiz/quiz-questions.js`,
  `quiz/quiz-engine.js`). Loaded by `buildCoreScript()`, and by
  `tests/helpers/load-engine.js`'s vm sandbox — this is what let the AI's
  existing chat-based calculator (`tryCalculators` in
  `matching-engine.js`) start calling the SAME `compoundInterest`/
  `peRatio`/`dividendYield` functions the new Calculators view uses,
  instead of maintaining the formulas twice.
- **`FEATURE_UI_MODULE_ORDER`** — real DOM manipulation
  (`quiz/quiz-ui.js`, `calculators/calculators-ui.js`,
  `lessons/lesson-progress-ui.js`, `stocks/stock-view-ui.js`,
  `compare/compare-ui.js`). Loaded by `buildFeatureUiScript()`, concatenated
  right after the shared logic, but deliberately NOT loaded into the test
  vm sandbox — these get DOM/jsdom verification instead, the same split
  already used for `storage.js`/`router.js` vs. the AI engine.

### Persistence (storage.js additions)

`getLessonProgress`/`markLessonComplete` (`{completed:[], lastVisited}`)
and `getQuizProgress`/`recordQuizAttempt` (`{bestScore, attempts,
lastAttemptAt}`) — the actual data shapes Phase 2 deliberately deferred
until a real feature needed them. `recordQuizAttempt` only overwrites
`bestScore` on a strictly better result — a worse attempt increments the
count without erasing a prior high score.

**Testing these required a real capability gap to be closed first**: the
vm-based test sandbox had no `localStorage` at all, so `storageAvailable()`
always caught a `ReferenceError` and returned false — every persistence
function silently no-op'd in every test that touched it, and only the
"storage unavailable" fallback path was ever actually exercised. Added a
minimal in-memory `localStorage` polyfill to `tests/helpers/load-engine.js`'s
sandbox so `tests/core/persistence.test.js` verifies the real read/write/
merge logic, not just its failure mode.

### Stock View

### Comparison

Two search inputs → both resolved and fetched in parallel → a genuine
side-by-side table, not AI-generated prose. Directional metrics (daily/
monthly change) may highlight which side is ahead; **ambiguous ones
(P/E, volatility) never get winner styling** — showing both numbers,
undecorated, is the entire point of "don't declare a winner the data
doesn't support." When fundamentals aren't available for both sides, P/E
is left out of the table entirely with an explicit note, not shown as
partial/misleading data. The "Ask the AI" handoff **primes
`aiConversationContext` directly** with both resolved entities
(`recordActiveEntity` called twice) before sending a message — naming both
companies in one fresh chat message does NOT trigger Phase 3's
entity-comparison mechanism (that requires the two entities already in
context from prior turns), so priming context first is what makes the
handoff a genuine comparison answer on the very first message rather than
an answer about only one of the two companies. Reachable at `#compare`.

### Two class-name collisions found and fixed (a pattern worth knowing about)

New view CSS classes collided with pre-existing, unrelated site classes
TWICE this phase:

1. `.quiz-opt`/`.quiz-explain` — already used by the 8 lesson-embedded
   quizzes (always in the DOM). A global reset tied to that class (on
   language switch) would have silently desynced the new Quiz view's
   visual state from its session state. Fixed by renaming the new view's
   classes to `.quiz-view-opt`/`.quiz-view-explain`.
2. `.compare-row` — already used by a lesson's real-vs-false-breakout
   chart comparison layout, with a DIFFERENT grid definition. The later
   CSS rule would have silently won, breaking the new Comparison view's
   column layout. Fixed by renaming the new view's classes to a
   `.cmpview-*` prefix.

**The general lesson**: before naming a new CSS class in this codebase,
`grep` the existing class name first — an 8-lesson-plus-quiz-plus-charts
site already has a lot of established naming, and "descriptive but generic"
names (`quiz-opt`, `compare-row`) are exactly the ones likely to already
exist for something unrelated. This is the same category of bug as the
`sma()` JS collision from Phase 2, just in CSS instead of JS.

### A `String.replace()` bug worth remembering

`buildSite()`'s two `template.replace(marker, content)` calls used a STRING
as the replacement argument. JavaScript treats sequences like `$&`, `` $` ``,
`$'`, `$$` specially inside a string replacement — even for a plain-string
search pattern. This codebase's own JS legitimately contains the literal
substring `$'` (e.g. `` '$'+price.toFixed(2) `` for formatting a dollar
amount, which appears in `stock-view-ui.js` and `compare-ui.js`), and `$'`
means "insert everything after the match" — silently corrupting every byte
of the built file from that point on. Caught because the corruption
produced a syntax error downstream (not at the actual corruption site,
which cost real debugging time to trace back). Fixed by switching both
`.replace()` calls to a FUNCTION argument (`template.replace(marker, () =>
content)`) — a function's return value is inserted literally, with no
special-pattern interpretation at all. **Never revert this to a plain
string replacement**, no matter how harmless a future edit looks — any
content containing a literal `$'`, `$&`, `` $` ``, or `$$` will silently
break the build again.
